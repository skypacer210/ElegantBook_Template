# 面向独立学院教育的多态智算调度平台研究
          
本研究针对小规模院校（特别是三本院校）算力资源分散式建设导致的利用率低下、运维困难等问题，提出构建独立学院专属的智算调度平台。通过微服务架构设计实现多模态数据融合与动态资源分配，采用K8s数据采集器与多类型数据库构建监控体系，创新性地运用算力漂移、细粒度切分等技术提升闲置资源利用率。该平台整合了自建、租赁与云端算力资源，形成包含访问层、服务层、管控层的分层架构，可满足AI for Science科研范式下跨学科、跨场景的算力服务需求，为应用型院校提供高可用、可扩展的智能算力解决方案，实现算力资源动态分配、多模态数据融合与跨场景协同，满足低成本、高弹性灵活独立学院教育用算场景需求。        


# 1. 选题依据

## 国内外研究现状

随着数据量的快速增长和智能化需求的不断扩大，各领域对智能算力的需求日益强烈，各行各业纷纷开始建设智算中心。智算中心是基于最新人工智能理论，采用领先的人工智能计算架构，提供人工智能应用所需算力服务、数据服务和算法服务的公共算力新型基础设施。

科研场景用算特点：
1. 需求波动显著 ：科研项目周期性的立项/结题阶段带来突发性算力需求，GPU资源使用率波动幅度达300%。
2. 学科交叉特征 ：多学科（如材料模拟、生物信息、流体力学）软件堆栈存在兼容性冲突，环境部署耗时占比超40%
3. 数据密集型计算 ：分子动力学模拟等典型场景单任务产生TB级中间数据，存储I/O压力达企业级应用的5-8倍
4. 长时计算依赖 ：量子化学计算等任务持续运行120+小时，对计算节点稳定性要求超出常规教学场景3个数量级
5. 安全合规要求 ：涉及国防、医疗等领域的科研数据需符合等保2.0三级要求，催生计算隔离与加密传输的特殊需求


国内高校算力管理平台现状：
1. 建设模式：以分散式建设为主，87%的985院校采用独立建设模式。部分通过购买硬件资源自主搭建集群，缺乏统一管理与调度，资源利用率低，平均硬件使用率80.75%，设备平均使用年限5.5年；部分学院通过租用公有云资源，缺乏对资源的精细化管理与调度。有近一半的硬件设备未放置在专业机房。具体而言，首先，院系单位各自购置的集群一般面向本单位内部人员，由于学科计算任务时长、资源需求的差异性，同一时间段内不同集群之间实时利用率极度不平衡，导致学校整体资源利用率较低；其次，由于其不对本单位外部用户提供服务，需要各自制定一系列使用制度规范并维护账户体系，然而各院系单位缺少专职的技术人员负责集群的整体运营和运维工作；最后，由于建设专业机房对技术和成本的要求较高，大部分硬件设备都被放置在实验室或者办公室。综上所述，分散式算力集群建设不仅会导致学校整体资源利用率低、小集群运营困难，同时还会存在一定的安全隐患。
2. 服务能力断层 ：仅23%平台支持异构计算框架，FPGA等新型计算单元覆盖率低于15%。首先，服务类型较少，无法满足校内多种算力需求场景。除个别学院用户有较强Linux功底能使用8卡独占节点外，其余学院用户普遍有单卡按量使用的需求场景，然而平台只提供公共集群调度器的方式，缺少主流的GPU虚拟化技术以及容器化的调度方式。其次，科研软件部署较少，部署运维软件能力欠缺。公共集群只安装了基础AI框架，缺少其他学科计算软件以及在线IDE编译环境，对计算机能力较弱的学科并不友好。
3. 技术选型：61%平台采用公有云+私有云混合部署，但跨云调度延迟中位数达380ms。虚拟化技术KVM应用占比72%，容器化部署比例不足40%，GPU直通技术普及率仅28%；
4. 计费维度单一 ：89%平台仅支持CPU小时计费，缺乏内存/存储/网络等多维度计费模型。计量计费模式与校内使用场景不相符。校内科研场景大多以项目的形式开展，一个导师指导课题组若干学生，导师负责支付算力费用，学生负责使用算力，项目下所有使用资源均应计入项目维度，而平台只在个人维度上计量计费，导致多个学生共用一个导师账号和数据目录，无法组建项目组，与校内实际运营场景不符。
5. 能效监控缺失 ：仅12%平台具备功耗感知能力，碳排放计量功能实现率为0。
7. 安全体系滞后 ：等保三级认证通过率不足45%。

国外高校算力管理平台现状：
1. 建设模式：联盟化运营 ：MIT-IBM联盟等跨机构算力池覆盖率达68%，资源复用率超92%；云原生架构 ：85%顶尖院校采用Kubernetes联邦集群，多云协同响应时间<50ms。
2. 技术层面：智能调度算法 ：Stanford采用的强化学习调度器使GPU利用率提升至89%；存算一体架构 ：剑桥大学光子计算芯片实现存储墙突破，能效比提升400%。
3. 生态特征：开源社区深度参与，85%平台基于OpenStack等开源框架二次开发，代码贡献率超30%；产学研协同，ETH Zurich校企协同平台年技术转化收益达2.3亿欧元。

需求与算力不匹配：
1. 调度模式匹配度不足：独立学院因算力需求低频、多模态（如AI课程与虚拟实训并存），传统调度模型难以适配，且缺乏针对教学行为数据的多模态融合治理机制。
2. 混合云算力管理与安全优化：混合云场景下，容量调峰与灾难恢复技术已成熟应用于企业级系统，但教育领域落地案例较少。多云环境下的数据隐私保护与跨域传输效率矛盾突出，现有加密技术难以兼顾低延迟与高安全性；AI驱动的动态负载预测模型在小规模场景中泛化能力不足。
3. 异构资源调度与跨集群协同：现有平台多面向大规模数据中心或公有云场景，缺乏针对小规模独立学院碎片化需求的轻量化调度模型，特别是边缘场景。
4. 多聚焦通用算力场景，未针对教育多态需求（如教学、科研、管理任务混合）设计分层调度策略，且缺乏轻量化部署能力。通用算力调度框架：AWS Batch与Google TPU集群通过Kubernetes实现多云资源编排，支持大规模AI训练任务，但缺乏垂直场景优化，动态调度策略以性能优先，忽略教育场景的成本敏感性与公平性需求。国外平台在国产化硬件兼容、数据主权保护（如《科技伦理审查办法》要求）方面存在政策壁垒，难以直接应用于国内教育场景。发现当前校内算力资源不足以满足各类科研需求，不适合用于训练垂直领域大模型相关的科学研究。调研数据表明：有96%的被调查者认为当前算力不能满足或仅能基本满足其科研需求；有95%的被调查者在未来有科研计算需求；有59%的被调查者期望未来以按需租赁的方式获取计算资源，有83%的被调查者愿意将硬件设备托管至学校机房。由此可见，校内算力需求与当前可提供的算力之间存在强烈的供需不平衡。
5. 垂直场景适配不足：现有调度平台多面向大规模智算中心或企业混合云，独立学院的小规模、碎片化需求缺乏针对性优化，硬件资源利用率普遍低于50%。



## 选题目的和意义&价值

针对独立学院算力需求碎片化、国产化适配弱、隐私要求高的核心矛盾，构建轻量化多态智算调度平台，突破“资源利用率低-场景适配差-安全成本高”的三角困境。

1. 通过算力插件、网关和编排调度技术，实现了跨域异构算力的统一纳管与动态分配，支持“东数西算”场景下的算力资源共享，资源利用率提升30%-50%110，智算平台所具备的算力服务能力极度契合教学科研一体化弹性算力范式用算需求，能为基础研究和前沿科学技术研究提供算力支持。
2. 教育公平与数字化转型：通过普惠算力支持，缩小独立学院与综合性大学的数字鸿沟，响应《算力基础设施高质量发展行动计划》中“低成本、高弹性”目标。推动教育公平，缩小与综合性大学的数字鸿沟，支持“人工智能+教育”融合创新。
3. 小规模院校的特点和必要性：独立学院因算力规模小、需求碎片化，传统调度模型难以适配，需研究基于边缘计算的本地化资源池调度策略。

# 2. 研究内容

## 研究目标

本文的研究目标是通过构建独立学院专属的智算调度平台，实现算力资源动态分配、多模态数据融合与跨场景协同，解决轻量化调度与教育场景适配。面向小规模院校的轻量化调度算法、多模态数据（教学行为/科研实验）融合治理、低门槛应用开发。

第一，全局优化异构分散算力。突破混合云（自建+租赁）异构算力（CPU/GPU/NPU）的动态纳管瓶颈，设计多目标调度算法，实现资源利用率提升≥50%，任务平均响应延迟降低≤30%。
第二，解决教育场景深度适配：
1. 开发面向低频突发需求的边缘优先调度模型，通过本地资源池优先响应AI教学、虚拟实训等任务，跨域传输开销减少≥40%。作为边缘计算节点、用算高峰时弹到公有云算力。
2. 校内智算体支持：训练资源分配与管理：为校内科研团队与教学项目分配专用的国产算力资源用于模型训练。私有化推理服务部署：在校内搭建私有化推理服务环境，确保训练好的模型能够在安全、隔离的校内网络中进行推理应用。
第三，构建多模态数据（学情文本/课堂视频/科研实验）融合治理框架，支持隐私计算（联邦学习+差分隐私），数据可用性提升35%且满足等保2.0三级标准。

# 3. 思路方法

## 研究方法

在本项目中，我们将采用混合研究法和实验验证的研究方法。从理论分析到平台搭建，再到实验验证，针对拟解决关键问题展开研究。

1. 首先搜集校内用户用算的场景，通过访谈以及实际数据采集，刻画资源需求特征，调研用户确定运营机制，同时研究参考国内外优秀算力平台搭建经验，优化独立学院场景适配性，确定对平台的功能需求。

2. 其次，将聚焦于算力平台搭建，采用开源框架结合自研算法搭建平台。通过平台搭建，实现对自建智算中心、租赁智算中心、所属企业算力集群3类异构智算中心的统一纳管，满足算力服务化、平台运营、运维一体化算力使用需求。在试点院校搭建平台，搭建容器化资源池，采集实时运维数据。

3. 在关键技术上采用仿真与实地部署相结合的方法，验证平台的可行性。模拟XXX，探究平台解决算力调度、纳管的性能与效率。利用CloudSim模拟混合云环境，验证调度算法性能。

4. 最后进行功能与性能测试，与国内外同类平台进行横向对比，分析其优势与不足。


## 技术路线

智算管理平台建设1个统一的智算管理技术架构，提供智算资源服务、容器编排服务、资源监控服务和运营管理服务4大核心服务，构建独立学院专属的智算调度平台，实现算力资源动态分配、多模态数据融合与跨场景协同，实现对自建智算中心、租赁智算中心、所属企业算力集群3类异构智算中心的统一纳管，满足算力服务化、平台运营、运维一体化算力使用需求。智算管理平台采用微服务架构，各子系统技术解耦，确保各类功能独立自洽，支持并行研发和独立演进，故障影响范围可控。主要技术涉及各类算力技术体系的整合接入、数据库体系、研发支持、集成实现、统一运维等领域。基于云原生架构设计搭建，扩展智算节点处理能力，实现资源、数据、平台三位一体，形成高可用、高性能、可持续交付的智算管理平台。包括如下四个功能：

1. 算力纳管

混合云集群统一管控：支持跨云、跨地域的集群统一接入、资源管理、授权管理等，集群类型可以包括：- 云服务商自建集群：通过云服务商平台基于自家基础设施上创建的 K8s 集群，如公有云火山引擎 VKE 集群- 注册集群：满足 CNCF 标准的第三方 K8s 集群，如阿里云 ACK、华为云 CCE、以及 IDC 自建的 K8s 集群。- 多云集群：由云服务商提供的运行在第三方云服务商（如AWS）基础设施之上的 K8s 集群。- 本地集群：由云服务商提供的运行在客户数据中心基础设施之上的 K8s 集群。

跨云/集群弹性能力：应用副本在多集群场景下的 HPA 弹性伸缩能力，支持在多集群管控面统一制定弹性伸缩策略（包括指标、阈值、弹性范围等），并在所有可调度的集群范围内根据集群资源情况进行最优弹性伸缩。

2. 资源调度

多云应用类型兼容：支持对 K8s 原生资源、CRD 资源、Helm 等类型资源的多云/集群分发；对无状态、有状态、任务等多类业务应用的多集群调度能力进行优化；可提供开箱即用的应用生态能力；将多集群资源封装为多云应用，通过模版、低门槛的方式降低云原生的使用难度。

跨集群调度能力：资源多集群分发策略支持程度，策略类型包括部署策略、差异化覆盖策略：- 部署策略：可通过指定集群、集群标签、集群污点容忍等进行集群筛选，并支持按照动态/静态权重进行应用副本跨集群调度、关联资源跟随分发、已存在资源无缝接管等能力；- 差异化策略：可将部署到不同集群资源进行覆写操作，如镜像版本、标签等。

多云应用容灾能力：- 故障迁移能力：为了提高业务的高可用性，针对多集群应用，当集群发生故障或应用在该集群中无法正常部署时，需要进行自动/手动故障迁移，进而保证用户业务的可用性与连续性。- 备份容灾能力：将应用元数据、卷数据手动(定期)备份到对象存储仓库中，待需要时可将备份数据进行恢复，可支持单集群应用容灾、跨集群/地域/云厂商应用容灾与迁移能力。

3. 资源运维

多云集群统一运维：- 支持多云异构环境管理下的统一日志、监控等收集与展示；- 支持以集群组或联邦集群维度的全局/聚合监控能力

作业视图：提供统一资源视图，实现对集群资源和作业的全方位实时监控。

4. 资源运营

资源订购中心，主要支持用户进行智算资源的订购退订等操作，实现和底层智算平台的资源校验并开通资源，同时也提供多维度的资源数据查看和统计。统一资源订购入口，支持多样化资源需求统一下单，统一校验，统一调度，实现算力“一点接入，即取即用”。

租户管理：用户中心模块提供与统一身份管理平台的对接，实现组织和账号的集中管理；统一的授权中心，实现细粒度的权限管理和授权管理。

## 技术融合创新

1、提出“轻量化分层调度模型”，基于云原生k8s插件实现

针对独立学院资源规模小、需求碎片化的特点，优化传统独占式调度策略。提出“边缘节点-区域中心-公有云”三级拓扑架构，通过动态权重分配算法（DWA）优先调度本地资源池，通过本地资源池优先响应突发任务，减少跨域传输开销，降低整体时延。系统性解决独立学院算力场景的碎片化与低效难题，为教育普惠算力提供可复制的技术范式。

第一、采用分层拓扑设计。边缘节点部署于校内机房，优先响应AI教学、虚拟实训等低延迟任务，覆盖80%日常需求；区域中心整合区域内多所院校资源，处理跨校协作任务（如联合科研项目）。公有云用于应对弹性扩展突发性峰值需求（如结题阶段算力需求激增）。

第二、动态权重分配算法（DWA）。
1. 基于实时负载、网络延迟与任务优先级动态计算调度权重；
2. 通过多种组合能力进行空间和时间维度上的闲置算力填充，最大化利用闲置资源
3. 算力超分、算力细粒度切分、通过算力漂移进行碎片整理、多机多卡聚合、算力自适应。
4. 日常作业视图可视，及时感知故障感知与智能运维，确保任务可持续不间断，提升算力利用率。

第三、开发定制化调度器（Scheduler Plugin），支持边缘节点自动注册与资源状态同步。集成Prometheus实现拓扑感知，动态调整Pod分配策略（如GPU密集型任务优先绑定边缘节点）。

第四、推理任务加速：从软件到硬件再到框架，分布式推理优化，如何利用消费级显卡实现推理。推理系统核心优化有哪些？软件加速：通过硬件加速库、编译器优化、算法优化、内存检查点加速等手段，提升推理性能;硬件加速：通过GPU/NPU等硬件加速设备，提升推理性能;框架加速：通过框架优化，提升推理性能。
 

2、模型动态安全保障：

采用模型动态加密，采用结构加密（增加伪分支）、权重加密（替换为伪权重）、算子加密（增加伪算子）的方式对模型结构进行混淆加密，确保模型可用不可见，保护模型运行安全。设计自适应加密算法，可针对不同模型，自适应调整和组合不同强度的结构加密、权重加密以及算子加密技术，保护模型安全的同时，也保障部署可行性和推理性能。


## 应用&运营模式创新

教学-科研-管理一体化平台：集成AI备课助手（基于DeepSeek模型）、虚拟实训系统（如MetaClass）与资源运营中心，支持按需调用算力单元（1 TFLOPS·小时），降低使用门槛50%。

设计“教学-科研-管理”一体化平台，支持教师快速生成智能教案（参考DeepSeek案例），学生通过虚拟智能体进行实训。

打造联合运营机制，由学校信息化领导小组牵头，信息技术中心作为技术与运营单位，各学院（系）作为众筹成员单位，组成联合运营小组，拟定联合运营草案，对校内众筹式算力建设与运营进行自上而下的顶层设计，提出“数字化运营、高效协作、众筹共享、合作共赢”的运营理念，主要聚焦如何以众筹式算力赋能高校科研团队普惠算力需求。像用水、用电一样，使用算力，像交水电费一样交算力费；

运营机制主要分为以下部分。
1. 首先，针对各众筹成员单位，作为硬件资产拥有者，对自有资源拥有优先使用权，在资源有空闲的情况下授权信息技术中心为校内其他用户提供算力租赁服务。
2. 其次，针对信息技术中心，作为统一运营方，通过众筹智算平台纳管计算资源或接管各成员单位原有计算平台，负责硬件侧的故障排查报修、平台侧的运维、科研软件侧的安装调试、用户侧的答疑与培训；
3. 校级智算管理平台面向校内用户提供统一门户官网，对接众筹智算平台及各子集群计算平台，建立动态定价与生态激励机制：参考“算力券”模式，设计基于Shapley值的资源贡献度量化算法，鼓励院校间算力共享，解决共享资源池的“公地悲剧”问题，预计提升资源利用率45%。同时，完善资源试用、充值缴费、论文奖励申请等审批流程线上化，方便校内师生快速申请资源，减少线下处理时间。
4. 最后，在收费方面，运营小组严格遵守北京邮电大学世纪学院收费管理小组发布的收费标准，对校内用户收取低于市场价的费用，对资产所属单位用户不收取费用或收取折扣价格。设计“教学-科研-管理”一体化平台，支持按需调用算力单元（1 TFLOPS·小时），降低使用门槛50%。
4. 生态机制创新：引入动态资源定价与积分奖励机制（如GpuGeek模式），鼓励院校间算力共享与学术成果转化。
